# Практика 3: Job и Registry

Эта часть закрывает пункты **1 (Job)** и **2 (Registry)** задания p3 и добавляет относящиеся к ним тесты из пункта 6. Базой служат существующий S1 и [диаграмма практики 2](architecture.md#состояния-job).

## Job

`mars/domain.py`: неизменяемый снимок Job. Метод `transition(...)` возвращает новый снимок с тем же ID. Вызывающий код сохраняет его через хранилище; исходный объект сохраняет прежнее состояние.

Разрешены переходы:

| Исходное состояние | Следующие состояния |
|---|---|
| `CREATED` | `EXTRACTING_TRANSCRIPT`, `CANCELLED` |
| `EXTRACTING_TRANSCRIPT` | `ANALYZING`, `FAILED`, `CANCELLED` |
| `ANALYZING` | `COMPLETED`, `FAILED`, `CANCELLED` |
| `COMPLETED`, `FAILED`, `CANCELLED` | Переходов нет |

Каждый запрещённый переход, включая повтор текущего состояния, вызывает `JobTransitionError` с кодом `INVALID_JOB_TRANSITION` и полями `from_status`, `to_status`. Правило находится внутри Job. Исключение наследуется от `ValueError`, сохраняя совместимость с обработчиками прежней реализации.

Конструктор, восстановление снимка и переход проверяют согласованность данных:

- Состояние должно быть одним из шести перечисленных.
- Результат обязателен только у `COMPLETED`, соответствует режиму и содержит непустые тезисы. При завершении таймлайна переданные `source_starts` дополнительно ограничивают таймкоды исходными субтитрами.
- Ошибка обязательна только у `FAILED`, содержит непустые строковые `code` и `message`.
- Нарушение вызывает `JobStateError`: `INVALID_JOB_STATE`, поле `status`, `result` или `error`.

Прямой переход существующей Job из `CREATED` в `COMPLETED` запрещён. При этом разрешено создание **новой** Job сразу в `COMPLETED` с проверенным готовым результатом: это предусмотренный диаграммой путь S5. Данная доработка не реализует поиск или политику хранения кэша.

## Registry

`mars/registry.py`: получает словарь `имя → объект Tool` либо последовательность пар. Возвращает тот же экземпляр по точному имени, без создания Tool и знания конкретных алгоритмов. Имена чувствительны к регистру. `operations()` возвращает кортеж зарегистрированных имён.

- Неизвестное имя: `UnknownOperation`, код `UNKNOWN_OPERATION`, поле `operation`.
- Повторное имя в последовательности пар, пустое/нестроковое имя либо объект без вызываемого `run`: `InvalidToolRegistration`, код `INVALID_TOOL_REGISTRATION`.
- Входной словарь копируется: его последующее изменение не меняет регистрацию. Для обнаружения повторных имён передавайте последовательность пар: Python-словарь уже не содержит повторяющихся ключей.
- Прежний импорт `from mars.tools import Registry` сохранён для сборки и тестов S1. Новый прямой импорт — `from mars.registry import Registry`.

`UNKNOWN_OPERATION` — ошибка доменного Registry. Ответ существующего HTTP API на неподдерживаемый режим по-прежнему проверяется до создания Job: `422 UNSUPPORTED_OPERATION`.

## Проверки З1–З6

Тесты `tests/test_job_registry.py` используют только стандартную библиотеку. В них нет HTTP, SQLite или обращений к YouTube. Обычный путь проверяется для `brief` и `timeline`; ошибки регистрации и неизвестная операция проверяются отдельно.

| Атака | Тест уровня Job | Что проверяет |
|---|---|---|
| З1: два исполнителя | `test_z1_start_an_already_running_job_again` | Уже работающую Job нельзя снова запустить |
| З2: перезапуск | `test_z2_late_result_after_interrupted_processing` | После фиксации `PROCESSING_INTERRUPTED` поздний результат отклоняется |
| З3: отменённая Job ожила | `test_z3_late_result_after_cancellation` | Отмена на любом активном этапе запрещает дальнейший анализ и завершение |
| З4: ошибка превратилась в успех | `test_z4_late_success_after_tool_failure` | `FAILED` не переходит в `COMPLETED`, причина сбоя сохраняется |
| З5: успех без работы | `test_z5_cannot_complete_without_processing`, `test_z5_cannot_complete_without_a_valid_result` | Нельзя пропустить этапы или завершить Job без допустимого результата |
| З6: повторное выполнение | `test_z6_cannot_rerun_or_finish_a_completed_job` | Завершённая Job не запускается и не завершается повторно |

Job проверяет переходы одного снимка. Два исполнителя могут прочитать старые снимки одновременно: только атомарная операция хранилища определяет, какой переход сохранён. Job также не определяет самостоятельно, что процесс перезапустился или право обработки истекло. Это обязанности хранения и Dispatcher по контракту p2.

Для проверки этих границ в существующем интеграционном наборе `tests/test_scenarios.py` есть:

- `test_z1_only_one_worker_can_claim_the_same_job` — два конкурентных исполнителя получают только одно право обработки;
- `test_expired_lease_is_failed_and_stale_worker_cannot_write` — повторное открытие хранения, обнаружение истёкшего права и отказ старому исполнителю;
- `test_cancel_while_tool_is_running_discards_result` — запоздавший ответ работающего Tool после отмены отбрасывается.

Эти интеграционные проверки используют существующую SQLite-реализацию S1 и входят в полный набор тестов. Они дополняют отдельный запуск доменных тестов из README.
